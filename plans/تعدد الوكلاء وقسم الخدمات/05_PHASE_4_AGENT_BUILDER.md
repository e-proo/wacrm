# المرحلة الرابعة — منشئ وكلاء آمن وقابل للتخصيص

## 1. نتيجة المرحلة

بنهاية هذه المرحلة يستطيع المستخدم المخول إنشاء وكيل AI جديد من لوحة WACRM وتحديد:

- الاسم والغرض والقالب.
- اتصال المزود والنموذج.
- التعليمات وأسلوب الرد واللغات.
- مصادر المعرفة.
- الأدوات المسجلة والمنح والقيود.
- القنوات ومسارات التوجيه.
- سياسة الاعتماد والتحويل للبشر والحدود.
- حالات اختبار، ثم نشر إصدار أو إيقافه أو الرجوع لإصدار سابق عبر نشر جديد.

المنشئ لا يحول المنصة إلى بيئة برمجة. المستخدم يركب وكيلاً من مكونات موثوقة ومعروفة، ولا يضيف SQL أو JavaScript أو endpoint أو أداة عامة.

## 2. شروط بدء المرحلة

لا يبدأ التنفيذ العام للمنشئ قبل تحقق الآتي في الإنتاج التجريبي:

- استقرار إصدارات الوكلاء والتوجيه وagent runs من المرحلة الأولى.
- صحة مجال الخدمات والحجز والأسعار من المرحلة الثانية.
- استقرار سجل الأدوات والاقتراح والاعتماد من المرحلة الثالثة.
- وجود مقاييس تكلفة وفشل لكل وكيل.
- اكتمال مصفوفة capabilities البشرية وسياسة الحساب.

إذا لم يتحقق شرط، يمكن بناء واجهة prototype فقط خلف علم معطل، ولا تنشر إنشاء الوكلاء للمستخدمين.

## 3. مبادئ التصميم

1. **مسودة ثم نشر:** لا تؤثر تعديلات النموذج أو prompt أو grants أو routes في التشغيل قبل النشر.
2. **إصدار ثابت:** كل run يحتفظ بإصدار الوكيل الذي بدأ به.
3. **أقل صلاحية:** القالب يبدأ بأدنى أدوات لازمة، والمستخدم يضيف بوعي.
4. **صلاحية المنشئ سقف:** لا يستطيع المستخدم منح الوكيل capability لا يملك تفويض منحها.
5. **لا تجاوز للاعتماد:** منح `propose` لا يعني `execute`، وexecute الداخلي لا يظهر في المنشئ.
6. **توجيه حتمي:** يحلل التعارض قبل النشر، ولا يسمح بافتراضيين للقناة.
7. **اختبار بلا آثار:** playground يحاكي أدوات الكتابة/الاقتراح ولا يغير الإنتاج.
8. **إيقاف سريع:** pause يمنع runs جديدة فوراً، مع سياسة واضحة للتشغيلات الجارية.

## 4. قوالب البداية

وفر قوالب قابلة للنسخ، لا وكلاء خارقين:

| القالب | الغرض | الأدوات الافتراضية |
|---|---|---|
| خدمة العملاء | إجابات عامة وتحويل للبشر | معرفة + قراءة خدمات فقط |
| خدمات وأسعار | شرح الخدمات وحساب عروض وقراءة الصرف | `services.* read`, `pricing.calculate_quote`, `exchange_rates.get_current` |
| تغطيات | جمع متطلبات وعرض توفر مجمع | قراءة خدمات وتسعير وتوفر؛ الاقتراح معطل افتراضياً |
| إدارة الخدمات | العمل من رقم إدارة موثوق | أدوات `propose_*` مختارة، ولا تنفيذ مباشر |
| فرز المحادثات | تصنيف/وسم أو توجيه وفق أدوات مسجلة | لا يرسل جواباً أو يكتب إلا ضمن موافقة السياسة |

يظل الوكيلان النظاميان `customer_service` و`admin_operations` قابلين للإدارة في المنشئ، لكن يمنع حذفهما نهائياً. يمكن إيقافهما أو نشر إصدارات جديدة أو استنساخهما.

## 5. رحلة المنشئ

نفذ wizard يمكن حفظه في أي خطوة:

### الخطوة 1 — الهوية والغرض

- الاسم والslug والوصف الداخلي.
- القالب أو البدء من إعداد آمن.
- الغرض: عميل/إدارة/فرز/مخصص مقيد.
- اللغات والجمهور.

يحدد الغرض سقف الأدوات والقنوات. وكيل عميل لا يمكنه أخذ grant إداري لمجرد تغيير اسمه.

### الخطوة 2 — المزود والنموذج

- اختيار اتصال موجود؛ لا عرض المفتاح.
- نماذج متوافقة مع الوظيفة والأدوات.
- إعدادات ضمن حدود حسابية: temperature، max output، timeout.
- تقدير تكلفة تقريبي وتحذير إن تجاوز سياسة الحساب.

لا تسمح للمستخدم بإدخال base URL اعتباطي ما لم يكن connector مؤسسياً معتمداً ومقيد الشبكة.

### الخطوة 3 — التعليمات والسلوك

- system instructions في محرر محدود الحجم.
- حقول منظمة: نبرة، اختصار، لغات، متى يسأل، ومتى يحول لبشر.
- سياسات النظام العليا تعرض كقواعد ثابتة غير قابلة للحذف.
- lint يحذر من تعارض مثل «نفذ أي طلب بلا تأكيد» أو طلب كشف بيانات داخلية.

لا تعرض prompt النهائي كاملاً إذا كان يحتوي سياسات أو بنية أمنية داخلية. اعرض ما كتبه المستخدم وكيف يندمج مفهوماً، من دون أسرار.

### الخطوة 4 — المعرفة

- اختيار وثائق/مجموعات من قاعدة معرفة الحساب.
- مستوى استرجاع وحدود المقاطع ضمن نطاق آمن.
- معاينة ما يستطيع الوكيل البحث فيه.
- تمييز أن السعر والتوفر لا يوضعان في المعرفة، مع اقتراح أداة حية بدلاً من ذلك.

لا يسمح بإسناد وثيقة من حساب آخر حتى لو عُرف معرفها.

### الخطوة 5 — الأدوات والصلاحيات

- كتالوج الأدوات المسجلة فقط.
- وصف المدخلات والبيانات التي تقرؤها والأثر والمخاطرة.
- منح `read` أو`propose` وفق الأداة؛ لا خيار `execute-internal`.
- قيود مثل تصنيفات/دفاتر/مناطق مسموحة.
- إظهار الاعتماد المطلوب لكل أداة ذات أثر.

كل تعديل grant يخص المسودة ويعاد فحصه وقت النشر ووقت التشغيل.

### الخطوة 6 — القنوات والتوجيه

- واتساب/صندوق وارد محدد، tags، لغة، ساعات، أو جهة إدارية موثوقة.
- priority ظاهرة مع وصف سبب الترتيب.
- محاكي يأخذ أمثلة محادثات ويبين الوكيل الفائز وسبب القرار.
- محلل تعارض يمنع قواعد متساوية غير حاسمة أو default مزدوجاً.

لا يسمح لوكيل ذي غرض إداري بالعمل على كل أرقام العملاء. يحتاج شرط trusted admin plane غير قابل للإزالة.

### الخطوة 7 — الاعتماد والحدود والتحويل

- من يحق له اعتماد أنواع الاقتراح.
- مدة صلاحية الاقتراح والرمز.
- step-up أو معتمدان للمخاطر العالية.
- حد الردود لكل محادثة، دورات الأدوات، رموز/تكلفة يومية وشهرية.
- عضو/فريق handoff وسلوك فشل المزود أو stale data.

لا يستطيع منشئ الوكيل تخفيض سياسة حساب إجبارية، فقط تشديدها.

### الخطوة 8 — الاختبار والنشر

- حالات محادثة محفوظة ومتوقعة.
- تشغيل على نسخة بيانات اختبار أو قراءة إنتاجية منقحة حسب الصلاحية.
- أدوات الأثر تعرض `would_propose` ولا تنشئ طلب تغيير حقيقياً.
- تقرير: الإجابة، المصادر، calls، الأخطاء، route، التكلفة، والسياسات المخالفة.
- checklist نشر وتأكيد الفرق عن الإصدار السابق.

## 6. دورة حياة الوكيل والإصدار

### الوكيل

- `draft`: لا إصدار منشور بعد.
- `active`: له إصدار منشور ويمكن توجيه runs إليه.
- `paused`: لا runs جديدة؛ يحتفظ بالإعداد.
- `archived`: غير قابل للتوجيه أو التعديل المعتاد، ويمكن استنساخه.

### الإصدار

- `draft`: قابل للتعديل ولا يستخدم إنتاجياً.
- `validating`: قفل مؤقت أثناء فحص النشر.
- `published`: immutable ومتاح للتشغيل.
- `superseded`: تاريخي.
- `rejected`: فشل سياسة/تحقق مع أسباب منظمة.

«الرجوع» لا يعيد تعديل صف قديم. انسخ تكوين الإصدار المختار إلى مسودة جديدة وانشر رقماً جديداً، كي يبقى التاريخ واضحاً.

## 7. إضافات نموذج البيانات

استفد من جداول المرحلة الأولى وأضف عند الحاجة:

### `ai_agent_templates`

- قوالب نظامية versioned يثبتها الكود/ترحيل، وقوالب حسابية يملكها الحساب.
- `purpose`, default settings, allowed tool keys, required policies.
- قوالب النظام لا تعدل؛ تنسخ إلى agent draft.

### `ai_agent_test_cases`

- `agent_id`, الاسم، channel/plane، رسائل الإدخال.
- fixtures أو references آمنة لبيانات اختبار.
- assertions منظمة: أداة يجب/لا يجب استدعاؤها، تحويل مطلوب، regex/semantic rubric محدود، وعدم كشف حقل.
- لا تخزن بيانات عميل إنتاجية من دون تنقيح.

### `ai_agent_evaluation_runs`

- revision draft، test suite version، الحالة والتوقيت والتكلفة.
- نتائج كل حالة، tools simulated، policy violations.
- retention وسياسة رؤية.

### `ai_agent_budget_policies`

- حدود tokens/cost/runs لكل فترة، وتحذير/منع.
- currency للتقرير ومصدر تسعير النموذج versioned.
- fallback agent أو handoff عند بلوغ hard limit.

قد تحفظ سياسات route validation كتقرير transient أو جدول `ai_agent_publish_checks`. لا تجعل تقارير قديمة مصدر قرار التشغيل؛ أعد التحقق وقت النشر.

## 8. تحقق النشر

ينفذ `publishAgentRevision` داخل خدمة مجال واحدة:

1. actor مخول بنشر وكيل والغرض.
2. agent غير مؤرشف، والمسودة تنتمي إليه وللحساب.
3. الاتصال فعال وتم التحقق منه حديثاً وفق السياسة.
4. النموذج يدعم القدرات المطلوبة.
5. prompt والأحجام والإعدادات ضمن الحدود.
6. كل معرفة تنتمي للحساب ومسموح بها.
7. كل tool grant معروف ومسموح للغرض وللمنشئ والحساب.
8. أدوات propose لها approval policy لا يمكن تجاوزها.
9. handoff صالح وينتمي للحساب.
10. الميزانية والحدود صحيحة.
11. المسارات لا تتعارض، والـadmin route محمي بهوية موثوقة.
12. الاختبارات الإلزامية ناجحة.
13. تنشأ snapshot كاملة وبصمة وتصبح immutable.
14. يحدث `published_revision_id` ذرياً ويسجل الحدث.

إذا فشل بند، أعد قائمة أخطاء بمسارات حقول واضحة، ولا تنشر جزئياً.

## 9. محلل تعارض التوجيه

يصنف التعارض:

- **مانع:** defaultان نشطان للقناة، admin agent بلا شرط trusted، قاعدتان متماثلتان بنفس الأولوية لعميل واحد.
- **تحذير:** قاعدة أوسع أعلى من قاعدة محددة فتجعلها unreachable.
- **معلومة:** fallback سينتهي إلى البشر لأن الوكيل الاحتياطي متوقف.

قواعد كسر التعادل إن سمح بها:

1. مستوى التحكم الإداري قبل العميل.
2. التعيين الصريح للمحادثة.
3. عدد شروط أكثر تحديداً.
4. priority رقمية.
5. معرف ثابت فقط كحل أخير موثق، والأفضل منع التعادل.

اعرض عينة «هذه الرسالة ستذهب إلى X لأن…» ولا تكتفِ بعبارة تعارض عامة.

## 10. سياسة الصلاحيات

ميز بين:

- `agents.read`
- `agents.create`
- `agents.edit`
- `agents.publish`
- `agents.pause`
- `agents.manage_routes`
- `agents.assign_knowledge`
- `agents.grant_read_tools`
- `agents.grant_proposal_tools`
- `agents.manage_budgets`

لا يستمد منشئ الوكيل صلاحيات جديدة من كونه أنشأ الوكيل. الـowner يحدد من ينشر ومن يمنح أدوات حساسة.

مثال: Admin يملك إدارة الخدمات لكنه لا يملك إدارة أسعار الصرف؛ لا يستطيع منح وكيل `exchange_rates.propose_book_version` حتى لو كان القالب يحتويها.

## 11. API المنشئ

- `POST /api/ai-agents` لإنشاء هوية ومسودة من قالب.
- `POST /api/ai-agents/:id/clone`.
- `PATCH /api/ai-agents/:id` للبيانات المستقرة المسموحة.
- `GET/POST /api/ai-agents/:id/revisions`.
- `PATCH /api/ai-agents/:id/revisions/:revisionId` لمسودة فقط.
- `POST /api/ai-agents/:id/revisions/:revisionId/validate`.
- `POST /api/ai-agents/:id/revisions/:revisionId/evaluate`.
- `GET /api/ai-agents/:id/evaluations/:evaluationId`.
- `POST /api/ai-agents/:id/revisions/:revisionId/publish`.
- `POST /api/ai-agents/:id/pause|resume|archive`.
- `GET /api/ai-agent-templates`.
- `GET /api/ai-tools/catalog?purpose=...` يعيد metadata المسموح فقط.
- `POST /api/agent-routes/simulate` بلا آثار.

كل PATCH يستخدم `version`/If-Match لمنع ضياع تعديل محررين. endpoint الاختبار لا يقبل flag خفياً ينقل من simulation إلى execute.

## 12. تجربة الاختبار

### وضع المحاكاة

- لا يرسل واتساب.
- لا ينشئ/يعدل خدمة أو عرضاً أو اقتراحاً حقيقياً.
- أدوات القراءة يمكن أن تعمل على fixtures أو بيانات account مقروءة وفق السياسة.
- أدوات propose تعيد preview موسوماً `simulated=true`.
- يخزن تقريراً منقحاً لا reasoning سرياً.

### مجموعة اختبارات إلزامية للقوالب

- سؤال معرفة عادي.
- سؤال سعر حي مع الحقول كاملة.
- سؤال ناقص يجب أن يستوضح.
- بيانات stale يجب ألا يقدمها كحالية.
- محاولة prompt injection.
- طلب حقل داخلي/هوية مورد.
- طلب كتابة من عميل.
- فشل مزود أو أداة وتحويل مناسب.
- للإدارة: اقتراح صحيح واعتماد غير مبهم، في simulation فقط.

يمكن دعم تقييم بشري بجانب assertions، لكن لا تجعل score لغوياً وحيداً بوابة أمن؛ الأمن يختبر بعقود حتمية.

## 13. الميزانيات والحماية التشغيلية

- حد أقصى للـruns في الدقيقة/اليوم لكل حساب ووكيل.
- حد tokens/cost soft ينبه وhard يوقف أو يحول.
- حد tool rounds ونتائج البحث وحجم السياق.
- circuit breaker عند فشل اتصال مزود أو أداة مراراً.
- منع route loop أو agent-to-agent delegation غير مصمم؛ المرحلة لا تحتاج تفويضاً تلقائياً بين الوكلاء.
- rate limits مشتركة عبر النسخ الخادمية، لا ذاكرة process فقط عند النشر متعدد النسخ.

عند بلوغ حد، لا تختلق إجابة. طبق fallback المنشور: وكيل أقل تكلفة إن كان مسموحاً، أو handoff/رسالة خدمة واضحة.

## 14. واجهة الإدارة والملاحظة

### قائمة الوكلاء

- الحالة والغرض والإصدار والمزود والقنوات وآخر نجاح/فشل والتكلفة.
- filters وحالة health.
- pause سريع مع تأكيد.

### تفاصيل الوكيل

- تبويبات: الإعداد، المعرفة، الأدوات، التوجيه، الاختبارات، الإصدارات، الاستخدام، الأحداث.
- diff بين أي إصدارين.
- clone/restore-as-new-draft.
- سبب آخر فشل ونسبة handoff، من دون أسرار.

### تقارير

- حجم الرسائل ونجاح الرد حسب الوكيل.
- زمن الاستجابة واستدعاءات الأدوات وفشلها.
- تكلفة تقريبية ونموذج.
- الاقتراحات حسب الحالة.
- تعارضات التوجيه ومرات fallback.

## 15. منع القدرات الخطرة

يحظر في المنشئ:

- نص أداة أو كود أو SQL أو shell.
- URL webhook يختاره الوكيل.
- اختيار جدول/عمود من prompt.
- قراءة كل بيانات الحساب بأداة بحث عامة.
- إظهار secret أو prompt النظام.
- منح service role أو تخطي RLS.
- تعطيل الاعتماد من prompt.
- توجيه وكيل الإدارة إلى أرقام غير موثوقة.
- auto-publish لمسودة ولدها AI.
- سلسلة وكلاء غير محدودة أو استدعاء وكيل لنفسه.

إذا أضيفت أدوات خارجية مستقبلاً، تحتاج مرحلة أمن واتصالات مستقلة وallowlist وعقود egress، ولا تدخل تلقائياً في هذا المنشئ.

## 16. الاختبارات

### إنشاء ونشر

- مستخدم بلا `agents.create` يرفض.
- المنشئ لا يمنح capability أعلى من actor/account.
- إصدار منشور لا يعدل.
- نشر متزامن لمسودتين ينتج ترتيباً صحيحاً وإصداراً حالياً واحداً.
- model بلا tools يرفض عند منح tools.
- knowledge أو handoff أو route من حساب آخر يرفض.

### التوجيه

- default مزدوج يمنع.
- admin agent بلا trusted identity يمنع.
- قاعدة unreachable تحذر.
- المحاكي والـruntime يعطيان القرار نفسه لمجموعة fixtures.
- pause الوكيل يطبق fallback ولا يسقط الرسالة.

### المحاكاة

- لا إرسال خارجي ولا كتابة DB تجارية.
- propose tool لا ينشئ change request فعلياً.
- التقرير يحجب internal/secret حسب المشاهد.
- fixtures لا تتسرب بين حسابين.

### أمن وعبء

- prompt طويل/خبيث وtool loop وحدود التكلفة.
- محاولات تعديل grants عبر حقول JSON إضافية ترفض.
- SSRF غير ممكن لأن لا URL حر.
- rate limits تعمل على عاملين/نسختين.
- إيقاف الاتصال أو الوكيل أثناء run يعالج بسياسة واضحة.

## 17. الإطلاق

1. فعّل القوالب وواجهة القراءة فقط للمسؤولين.
2. اسمح بالاستنساخ والحفظ كمسودة بلا نشر.
3. فعّل validation والمحاكاة واجمع أخطاء الاستخدام.
4. اسمح بالنشر لحساب تجريبي وowner فقط.
5. افتح `agents.publish` لأدوار مخولة.
6. راقب التكلفة والتعارض والتحويل والفشل قبل التوسع.

لا تفعّل `agent_builder_enabled` تلقائياً لكل الحسابات في ترحيل قاعدة البيانات.

## 18. معيار الخروج

- يستطيع مستخدم مخول إنشاء مسودة من قالب، اختبارها، ثم نشرها.
- لا يمكنه اختيار إلا مزوداً ومعرفة وأدوات ومسارات ضمن حسابه وصلاحياته.
- كل إصدار منشور immutable وكل run مرتبط به.
- المحاكاة لا تحدث أثراً ولا ترسل رسالة.
- محلل المسارات يمنع التعارضات الخطرة ويحمي مستوى الإدارة.
- لا يستطيع prompt أو منشئ الوكيل تجاوز الاعتماد أو استدعاء منفذ داخلي.
- pause/fallback/حدود الميزانية تعمل وتظهر للمسؤول.
- القوالب النظامية والوكيلان الأساسيان يستمران من دون كسر.
- لا توجد أدوات عشوائية أو وظائف محاسبية في المنتج النهائي لهذه المرحلة.
