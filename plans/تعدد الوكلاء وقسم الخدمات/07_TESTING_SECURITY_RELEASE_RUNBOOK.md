# دليل الأمن والاختبار والإطلاق والتشغيل

## 1. الغرض

هذه هي بوابة الجودة التشغيلية للمراحل الأربع. لا يكفي أن تعمل الشاشة في المسار السعيد؛ النظام يدير رسائل عملاء وأسعاراً متغيرة وقرارات قد تؤثر في تعاملات مالية، لذلك يجب إثبات العزل والدقة ومنع التكرار والرجوع الآمن.

هذه الوثيقة لا تحول النظام إلى منصة محاسبية. الأرقام هنا أسعار واقتباسات وكميات تشغيلية فقط.

## 2. نموذج التهديد

| التهديد | الأثر | الضوابط الأساسية | الاختبار الملزم |
|---|---|---|---|
| حقن تعليمات من عميل/معرفة/وصف | كشف بيانات أو طلب أداة خاطئة | فصل البيانات عن النظام، grants، schema، DTO redaction | prompts هجومية مع تأكيد عدم الوصول للhandler |
| انتحال مالك في نص واتساب | اقتراح/تنفيذ غير مصرح | الهوية من metadata مطبعة ومتحققة، لا من النص | رقم غير موثوق يكتب أمر الإدارة |
| اختطاف رقم إدارة | تغييرات حساسة | إلغاء سريع، token قصير، step-up/معتمد ثانٍ للـhigh | revoke أثناء جلسة واعتماد بعد الإلغاء |
| إعادة webhook/الاعتماد | رد أو تنفيذ مكرر | unique ids وidempotency وcompare-and-set | طلبات متوازية متطابقة |
| تسرب حساب لآخر | خرق بيانات | RLS، account-scoped queries، FK مركبة، DTOs | معرفات من حساب B في كل API لأعضاء A |
| تسرب مفتاح المزود | إساءة استخدام | تشفير، server-only، redaction، تدوير | فحص JSON/HTML/log/error/telemetry |
| سعر قديم أو معكوس | خسارة/تضليل | versions، buy/sell meaning، TTL/stale، أداة حتمية | انتهاء أثناء المحادثة واتجاهات متعددة |
| حجز زائد للتغطية | التزام غير قابل للتنفيذ | قفل صفوف/تحديث شرطي ومعاملة | حجز آخر كمية من عاملين |
| تغيير متزامن بعد preview | كتابة فوق تحديث جديد | expected version وconflicted | اقتراحان للأساس نفسه |
| مزود AI غير متاح/بطيء | توقف الرد أو تكراره | timeout، retry مصنف، durable run، handoff | timeout قبل/بعد tool وقبل/بعد send |
| tool loop/تكلفة غير محدودة | استنزاف | rounds/tokens/budget/rate limits | نموذج يعيد الأداة باستمرار |
| SSRF/تنفيذ كود | اختراق خادم | لا URL/SQL/code حر؛ registry مغلق | حقول إضافية تحاول تمرير URL/اسم جدول |
| صلاحيات service role واسعة | تجاوز RLS | تحقق مجال صريح وسياق موثوق | direct service test بحساب خاطئ |

## 3. سياسة الأسرار والبيانات

- لا ترسل مفاتيح المزود إلى client component أو browser logs.
- لا تستخدم متغيرات `NEXT_PUBLIC_*` للأسرار.
- لا تسجل Authorization headers أو webhook secrets أو OTP/confirmation token.
- اخفِ محتوى رسائل العميل من logs العامة؛ استخدم IDs ورموز أسباب وبيانات منقحة.
- لا تخزن chain-of-thought. خزّن الأدوات والحقائق والنتائج المنظمة اللازمة للتدقيق.
- حدد مدة احتفاظ للـrun inputs/tool results/change snapshots، مع مراعاة متطلبات العمل والخصوصية.
- ملفات تصدير التدقيق تطبق الصلاحيات نفسها، ولها رابط قصير العمر إن وجدت.
- تدوير مفتاح اتصال لا يتطلب كشف القديم، ويثبت آخر تحقق فقط.

## 4. هرم الاختبار

### 4.1 اختبارات وحدة

سريعة وحتمية، تشمل:

- موجه الوكلاء وترتيب القواعد.
- تطبيع الهاتف والتحقق من أمر الاعتماد.
- مخططات الحقول الديناميكية.
- decimal والتسعير والتقريب.
- stale/expiry واتجاه الصرف.
- انتقالات الحالات.
- effective permissions وأسباب الرفض.
- DTO redaction.
- provider error normalization.

لا تتصل بمزود خارجي حقيقي في unit tests.

### 4.2 اختبارات تكامل قاعدة البيانات

تعمل على PostgreSQL/Supabase اختبارية وتغطي:

- الترحيلات من قاعدة نظيفة ومن نسخة مشابهة للإنتاج.
- RLS لكل جدول وعملية.
- القيود المركبة وعزل الحساب.
- نشر الإصدارات ذرياً.
- claim/lease للـagent runs.
- حجز التغطية المتزامن.
- اعتماد وتنفيذ التغيير مرة واحدة.
- reconciliation بعد فشل مصطنع.

### 4.3 Contract tests

- كل provider adapter باستخدام fixtures مسجلة ومنقحة أو mock server.
- كل أداة: schema input/output، permission، timeout، redaction، idempotency.
- API response/error envelope.
- webhook event version.
- legacy `ai_configs` compatibility أثناء فترة الانتقال.

### 4.4 E2E

تغطي المتصفح ومسار webhook الوارد والرد الصادر بمحاكيات آمنة:

- إدارة المزود والوكيل والنشر.
- رقم الإدارة والتحقق والإلغاء.
- إنشاء تصنيف/خدمة/تسعير ونشرها.
- نشر أسعار صرف دفعة واحدة.
- عرض/طلب/مطابقة تغطية.
- سؤال عميل عن خدمة ورقم حي.
- اقتراح إدارة ثم اعتماد/رفض/انتهاء/تعارض.
- منشئ وكيل ومحاكاته ونشره وتوقفه.

### 4.5 اختبارات العبء والفوضى

- burst رسائل لنفس الحساب ولمحادثات متعددة.
- تكرار webhook بترتيبات مختلفة.
- عدة workers تدعي runs والحجوزات.
- timeout مزود قبل الرد وبعده.
- DB transient error عند transitions.
- نشر rate sheet كبير ضمن الحد.
- بلوغ budget/rate limit عبر نسختين خادميتين.

## 5. مصفوفة اختبارات حرجة

| السيناريو | النتيجة الوحيدة المقبولة |
|---|---|
| webhook نفسه 10 مرات | رسالة محفوظة واحدة، run واحد، رد واحد |
| رقم إدارة موثوق يرسل تحديث سعر | proposal فقط قبل الاعتماد |
| عميل يرسل الصيغة نفسها | لا أدوات إدارة ولا كشف أنها موجودة |
| «نعم» رداً على proposal | لا تنفيذ، وطلب صيغة صحيحة |
| اعتماد صحيح مرتين بالتوازي | تنفيذ واحد ورد نتيجة idempotent |
| تغير السعر بعد preview | proposal متعارض، لا overwrite |
| سعر stale | لا يوصف بأنه حالي ولا يخمن رقم |
| حجزان لمتاح 10,000، كل واحد 10,000 | نجاح واحد فقط |
| مورد هو نفسه طالب في طلب آخر | كلا السجلين صالحان بلا تغيير contact type |
| حساب A يمرر service ID من B | 404/رفض بلا تسريب وجود السجل |
| pause وكيل أثناء الانتظار | لا إرسال جديد مخالف؛ fallback وفق السياسة |
| حذف/تعطيل اتصال مستخدم | الحذف ممنوع، والتشغيل الجديد يتوقف بأمان |

## 6. اختبار RLS المنهجي

لكل جدول أنشئ fixtures:

- Account A: owner، admin، agent، viewer.
- Account B: owner وسجلات تحمل أسماء/slug مماثلة.
- مستخدم متعدد العضويات إن كان المشروع يدعمه.

نفذ لكل دور:

1. SELECT collection وby-id.
2. INSERT مع account صحيح وخاطئ.
3. UPDATE هدف صحيح وخاطئ وحقول محظورة.
4. DELETE/Archive.
5. RPC/SECURITY DEFINER إن وجدت.
6. joins وfilters وsearch؛ كثير من التسرب يحدث عبر join أو function لا endpoint البسيط.

عامل `NOT_FOUND` أفضل من كشف `FORBIDDEN` عندما يكشف الأخير وجود معرف بحساب آخر، وفق نمط المشروع.

## 7. اختبار الترحيلات

لكل مرحلة:

1. نسخة احتياطية قابلة للاستعادة في بيئة staging.
2. تطبيق كل الترحيلات من قاعدة نظيفة.
3. تطبيق الترحيل على snapshot من schema/data القديمة.
4. تشغيل backfill مرتين وإثبات idempotency.
5. قياس locks وزمن الترحيل على حجم مماثل للإنتاج.
6. التحقق من RLS والفهارس وقيود FK.
7. اختبار تطبيق قديم مؤقتاً مع schema موسع عند rolling deploy.
8. اختبار تطبيق جديد على حساب migrated وآخر legacy.

تجنب `NOT NULL` مباشر على جدول كبير قبل backfill والتحقق. استخدم expand/backfill/validate/contract. لا تحذف عموداً قديماً في الإصدار نفسه الذي يتوقف فيه الكود عن كتابته.

## 8. أوامر الجودة

من جذر مستودع WACRM وبعد تثبيت الاعتمادات بالطريقة المعتمدة للمشروع:

```bash
npm run format:check
npm run typecheck
npm run lint
npm test
npm run build
```

إذا كان الاختبار الافتراضي watch في بيئة معينة، استخدم صيغة Vitest غير التفاعلية الموافقة لـ`package.json`. لا تعدل scripts لمجرد إخفاء فشل.

شغل أيضاً:

- اختبارات قاعدة البيانات/RLS بالطريقة التي يعتمدها المستودع أو أضف script موثقاً.
- migration lint إن كان متاحاً.
- فحص secrets في diff وفق أدوات الفريق.
- اختبارات E2E للمسارات المعدلة.
- فحص أن كل مفاتيح الترجمة الجديدة موجودة في جميع ملفات `messages/*.json` الحالية.

يجب أن يسجل طلب الدمج الأوامر والنتائج، وأي فشل سابق غير متعلق مع دليل أنه سابق.

## 9. Definition of Done للكود

لا يعد العمل مكتملاً إلا عند:

- لا أخطاء TypeScript أو lint أو build أو tests.
- لا `TODO/FIXME` في مسار أمني أو تسعير أو اعتماد.
- route handlers رفيعة والمنطق داخل خدمات مجال قابلة للاختبار.
- schemas مشتركة بين API/runtime حيث يمكن، ولا تحقق يدوي متناقض.
- RLS وسياسة الخادم واختبار cross-account مكتملة.
- الأخطاء مصنفة ومنقحة وقابلة للملاحظة.
- feature flag ومفتاح إيقاف موثقان.
- migration/backfill/rollback أو forward-fix موثقة.
- الواجهة مترجمة ومتاحة بلوحة المفاتيح وتعرض loading/empty/error/conflict.
- الوثائق/API contracts محدثة مع الكود.

## 10. مراجعة أمنية قبل الدمج

يراجع شخص غير منفذ التغيير على الأقل:

- أين تأتي `account_id` والهوية والصلاحيات؟
- هل يستطيع النموذج أو body تزويرها؟
- هل الأداة ظاهرة لوكيل غير مخول؟
- هل handler يعيد التحقق أم يعتمد على القائمة المعروضة؟
- هل يوجد مسار كتابة لا يمر بالاعتماد؟
- هل يمكن replay أو race تنفيذ مرتين؟
- ما الذي يصل إلى log/telemetry/provider؟
- هل public DTO قد يكشف المورد/التكلفة/internal notes؟
- هل stale/timeout يفشلان مغلقين؟
- هل تعطيل flag فعلي على الخادم؟

## 11. استراتيجية feature flags

الأعلام على مستوى الحساب، والتحقق خادمي:

| العلم | الوضع الأولي | وظيفة الإيقاف |
|---|---|---|
| `multi_agent_enabled` | off | يرجع للحل القديم للحساب غير المقطوع |
| `service_catalog_enabled` | off | يخفي/يمنع endpoints الجديدة |
| `agent_live_reads_enabled` | off | يمنع أدوات القراءة ويرجع handoff |
| `admin_change_proposals_enabled` | off | يمنع صنع proposal من AI |
| `admin_change_execution_enabled` | off | يبقي proposal مرئياً ولا ينفذ |
| `agent_builder_enabled` | off | يمنع إنشاء/نشر custom agents |

أضف kill switch أوسع لأدوات AI ذات الأثر يمكن تغييره بسرعة ومن دون deployment إذا كانت بنية الإعدادات آمنة ومراقبة.

## 12. مراحل الإطلاق

### المرحلة الأولى

1. schema والكود مع flag off.
2. backfill staging ثم حساب داخلي.
3. shadow routing يسجل القرار ولا يرسل.
4. مقارنة القديم والجديد.
5. canary لوكيل العميل ثم الإدارة بلا أدوات أثر.

### المرحلة الثانية

1. إدارة يدوية داخلية.
2. بيانات تجريبية ومراجعة صاحب العمل.
3. نشر خدمات فعلية وأسعار مع audit.
4. تشغيل التغطيات بمستخدمين محدودين.

### المرحلة الثالثة

1. tools في simulation.
2. read-only للعملاء.
3. proposal-only للإدارة.
4. اعتماد من اللوحة.
5. اعتماد واتساب للعمليات المختارة.
6. high-risk مع step-up.

### المرحلة الرابعة

1. templates/read-only.
2. drafts بلا publish.
3. validation/evaluation.
4. owner-only publish.
5. أدوار وحسابات إضافية تدريجياً.

في كل خطوة حدد نسبة/قائمة حسابات، فترة مراقبة، معايير نجاح، وشرط rollback قبل التنفيذ.

## 13. المقاييس والتنبيهات

### AI والتوجيه

- runs queued age وstuck leases.
- success/failure/skip/handoff rates حسب agent/revision/provider.
- duplicate prevention hits؛ ارتفاعها قد يدل على webhook storm.
- زمن provider وtool وإرسال WhatsApp.
- tokens/cost/budget utilization.
- route no-match/conflict.

### الخدمات والأسعار

- عدد rate books الحالية/stale.
- عمر آخر سعر لكل سياق نشط.
- فشل quote validation.
- فرق غير متوقع بين preview والتنفيذ.

### التغطيات

- كميات active/reserved/fulfilled.
- فشل الحجز بسبب التزامن أو عدم الكفاية.
- حجوزات منتهية لم تحرر.
- نتيجة reconciliation وأي invariant violation.

### الاعتماد

- pending age، expired، invalid attempts، conflicted، failed executions.
- تغيير high-risk خارج ساعات/نمط الحساب.
- عدة محاولات رموز من هوية واحدة.

أمثلة تنبيه:

- run queued أطول من SLO.
- نسبة provider auth failures > 0 لاتصال فعال.
- دفتر مستخدم أصبح stale.
- أي reconciliation يجد `reserved + fulfilled > total/requested`.
- تنفيذ change request high-risk بلا event اعتماد مطابق — يجب أن يكون مستحيلاً ويعامل كحادث حرج.

## 14. مهام التشغيل الدورية

- مسترد `agent_runs` العالقة والمنتهية lease.
- إنهاء change requests والحجوزات بعد expiry بصورة idempotent.
- تحرير الحجوزات المنتهية داخل معاملة.
- تعليم دفاتر السعر stale/حسابها عند القراءة وإرسال تنبيه.
- reconciliation لكميات عروض/طلبات التغطية مع matches.
- aggregation للاستخدام والميزانيات.
- تنظيف بيانات logs/نتائج الأدوات وفق retention.

لا تعتمد على cron وحيد بلا قفل؛ كل مهمة تقبل التكرار وتستخدم claim/idempotency.

## 15. أدلة الحوادث

### 15.1 اشتباه تسرب مفتاح مزود

1. عطّل اتصال المزود فوراً.
2. أوقف runs الجديدة أو حوّل fallback.
3. دوّر المفتاح لدى المزود وخزنه عبر rotate flow.
4. راجع audit access وlogs وتأكد من redaction.
5. لا تعِد تفعيل الاتصال قبل verify.
6. وثق النطاق والمدة والحسابات المتأثرة.

### 15.2 نشر سعر خاطئ

1. أوقف `agent_live_reads` لذلك الحساب أو عطّل الدفتر.
2. لا تعدل الإصدار المنشور؛ أنشئ إصدار تصحيح وانشره.
3. حدد الردود/quotes التي استخدمت `book_version_id` الخاطئ.
4. أخطر المسؤولين واتبع إجراء العمل للتواصل مع العملاء.
5. راجع change request/approver والدليل، لا تمسح الحدث.

### 15.3 رقم إدارة مخترق

1. revoke الهوية الموثوقة.
2. أوقف تنفيذ الاقتراحات، وألغ pending الصادرة منها.
3. راجع change events منذ وقت الاشتباه.
4. استخدم dashboard/قناة آمنة لعكس التغييرات عبر إصدارات جديدة.
5. أعد التحقق من رقم جديد وسياسة step-up.

### 15.4 ردود مكررة

1. فعّل kill switch للرد التلقائي إن استمر الضرر.
2. افحص unique inbound/run/outbound idempotency.
3. قارن provider message id وWhatsApp send id.
4. أصلح الاسترداد أو lease من دون حذف السجلات.
5. اختبر replay قبل إعادة التفعيل.

### 15.5 عدم اتساق كميات التغطية

1. أوقف إنشاء matches الجديدة.
2. شغل reconciliation read-only وحدد السجلات.
3. لا «تصحح» الرصيد آلياً بلا مراجعة events.
4. طبق forward fix داخل معاملة مع event إداري وسبب.
5. أعد اختبار السباق الذي سبب الخلل.

### 15.6 عطل مزود AI

1. تحقق هل العطل اتصال واحد أم المزود كله.
2. طبق circuit breaker وfallback المنشور فقط.
3. لا تحول إلى نموذج غير معتمد بأدوات مختلفة تلقائياً.
4. استعد runs القابلة للإعادة؛ لا تكرر ما أرسل.
5. راقب backlog قبل إعادة فتح المعدل الكامل.

## 16. النسخ الاحتياطي والرجوع

قبل الترحيلات الجوهرية:

- snapshot/نسخة احتياطية مجربة الاستعادة.
- قياس RPO/RTO مناسبين للنشاط.
- حفظ قائمة flags والقيم الحالية.
- خطة رجوع تطبيق متوافقة مع schema الموسع.

الرجوع المفضل:

1. إيقاف العلم/التنفيذ.
2. إعادة الكود لمسار القراءة القديم إن كان ما زال مدعوماً.
3. الإبقاء على الجداول الجديدة وعدم حذف بياناتها.
4. forward fix للبيانات/الترحيل عند الحاجة.

لا تنفذ down migration مدمراً في الإنتاج إذا كانت جداول المرحلة استقبلت بيانات لا يمكن تمثيلها قديماً. وثق أن rollback تشغيلي لا حذف بيانات.

## 17. قائمة قبول المرحلة الأولى

- [ ] backfill idempotent من `ai_configs`.
- [ ] وكيلان نظاميان واتصالات/إصدارات مستقلة.
- [ ] قرار توجيه واحد وrun واحد لكل رسالة.
- [ ] جهة الإدارة تسبق flows العملاء.
- [ ] human takeover يمنع AI.
- [ ] run recovery وoutbound idempotency مجربان.
- [ ] secrets لا تظهر في أي مخرج.
- [ ] fallback/flag rollback مجرب.

## 18. قائمة قبول المرحلة الثانية

- [ ] schema حقول مرن versioned ومتحقق.
- [ ] أوصاف public/AI/internal منفصلة.
- [ ] decimal والتقريب والأمثلة صحيحة.
- [ ] rate sheet ذري وstale آمن.
- [ ] offer/request roles على السجل لا contact.
- [ ] partial matching ومنع overbooking تحت التزامن.
- [ ] DTO عام لا يكشف المورد/التكلفة.
- [ ] لا كيان محاسبي أضيف.

## 19. قائمة قبول المرحلة الثالثة

- [ ] propose tools لا تكتب الهدف.

## 21. قرار Go/No-Go

قرار الإطلاق لكل مرحلة يوثق:

- نسخة التطبيق والترحيل والـcommit.
- الحسابات/النسبة المشمولة.
- نتائج أوامر الجودة والاختبارات الحرجة.
- حالة النسخ الاحتياطي وتجربة الرجوع.
- لوحات المراقبة والتنبيهات ومالك الاستجابة.
- الأخطاء المعروفة وتأثيرها؛ لا تقبل أخطاء عزل أو أسرار أو تكرار أو أرقام.
- وقت بدء المراقبة ووقت القرار التالي.

الحالات التي تفرض **No-Go** بلا استثناء: فشل RLS، احتمال تنفيذ بلا اعتماد، تسرب سر/بيانات داخلية، حجز زائد، سعر stale يقدم كحالي، رد مكرر، أو عدم وجود مسار إيقاف آمن.
