# ADR-INBOX-002 — Verified WhatsApp channel identity & multi-session delivery
**Accepted by project owner 2026-11-21.** Supersedes the per-connection thread identity in ADR-INBOX-001; all its nonconflicting security, CRM, unread, API, cutover and no-Production gates remain. Design approved, NOT implemented or TEST/live verified. Scope: INBOX-0..6, before schema changes.

## 1. Identity model (authoritative)
- CRM contacts and parent conversations remain unchanged (unique account/contact).
- A channel is the durable operational identity of a WhatsApp sender/number **within an account and provider boundary**. OpenWA sessions for the same independently verified sender identity join one channel, not separate CRM threads. Different numbers remain distinct; Meta remains official/default and a separate channel/provider-policy domain even if displayed number matches. No cross-provider auto-merge or cross-account grouping. A future cross-provider interoperability decision demands distinct proof/ADR; no assumption that IDs match.
- Proposed whatsapp_channels(id,account_id,provider,verified_identity_key,identity_state,display_name,primary membership,version,...); identity keys server-managed (normalized verified E.164 or documented immutable provider account/phone identity), unique scoped verified identity, never expose native JID/credentials. Meta registry has no stored phone_identity in TEST: singleton by verified configured phone_number_id/provider_external_id and account; do not infer number or join to OpenWA.
- Proposed channel_connection_memberships(id,account_id,channel_id,connection_id,verified_at,evidence reference,valid_from,valid_until,identity_epoch,role/status). One active membership for a connection, historical memberships immutable; composite FKs account+channel/account+connection; provider consistency. Existing registry remains authoritative transport. Verification requires authenticated gateway status with exact session/instance and verified self identity; existing phone_identity is candidate only, mutable in current code (session-lifecycle.ts 121); no trust on admin-provided string, missing/mismatched/changed identity quarantined until verified. Do not use display name, sender contact phone, LID or same gateway URL. On re-pair with different phone, close epoch, create/link correct channel with audit, never remap historical messages; unknown historical epoch stays unresolved.
- Operational thread key (account_id, conversation_id, channel_id), one stable opaque thread ID, status, watermark, known unread, inherited/unallocated unread, preview. Keep originating connection_id, provider and provider_message_id on original messages. Channel-level message association and observations are additive; do not move/delete original records, change reply IDs or synthesize messages from broadcast recipients. Store message association with immutable membership epoch (or equivalent proven mapping) rather than dynamic mutable current phone. No direct client writes to projection/membership/provenance.

## 2. Inbound and outbound deduplication
- Distinguish physical webhook delivery, native message observation, and canonical logical message. Existing receipts 147 unique(connection_id,provider,provider_event_id) remain; current inbound 037 unique(conversation_id,message_id) may suppress a duplicate but discards second observation and is not scoped to channel. Current normalization falls back to envelope.eventId if native ID absent (inbound-normalization.ts 148): explicitly classify evidence as native vs event-only. Do not treat event-only IDs as stable cross-session identifiers.
- Proposed message_connection_observations (account,channel,thread,canonical message,connection,membership epoch,provider,native message id,delivery/receipt evidence,direction,observed_at,source,verification state) durable immutable route observations; unique scoped provider/connection/native key or event receipt key, native routing IDs server-only. Canonical dedup key includes account + channel + verified provider-native message identity namespace + direction/canonical peer when required by adapter contract. Prove identical native IDs across linked devices/engines or independently verified alias mapping; different strings are not proof of distinct or equal messages. Equal IDs across different channels may be legitimate; review 037 conflicts and every legacy reply/lookup before additive migration, preserve dedup through native scoped constraints. 
- In one DB transaction verify account/session/member epoch, lock/insert canonical identity, record each authenticated observation, create canonical message and update projection/unread/work claim only once. Duplicate event returns canonical id and inserts missing observation only; late/out-of-order events do not regress preview or delivery. Use existing shared inbound pipeline, atomically claim business fanout with durable idempotent effects/outbox and retry recovery (not a second agent/automation system); duplicate observation must not trigger reply correlation under a different reserved sender, schedule tasks, AI, flow, notifications or increment unread. No claim of “exactly once” provider dispatch; enforce idempotent logical effects. Preserve frozen task/broadcast sender; only use exact proven causal observation for existing correlation; if conflicting, review, never broaden authorization.
- If native ID missing, engine aliases differ with no documented trustworthy mapping, or identity cannot be verified: retain raw signed receipt/observations in existing deferred/reconciliation mechanism or additive scoped unresolved queue, no automatic merge by body/time/phone, no auto-response or duplicate outbound, surface review. If distinct strong IDs in a documented shared namespace, identical content is still two messages. Require tested native ID behavior for each supported engine before enabling same-channel multi-active ingress. Conservative initial safe mode: one admin-designated authoritative ingress connection per channel; secondary observations may be attached with proof or retained pending review, never silently dropped. If primary absent, explicitly audited ingress handover with bounded gap recovery, not auto-promote on ambiguous receipt. Secondary can observe genuinely missing primary ingress with proof when shared namespace verified. Do not suppress valid distinct messages based solely on session role. 
- For existing history, candidate grouping from stored phone identity only is not proof. Backfill proven epochs first, preserve all 725 rows; do not delete duplicate-looking rows. If confirmed duplicate historical rows ever exist, map canonical display alias while keeping originals/refs; unresolved mapping remains review. Backfill never invokes provider or business effects. Missing native IDs remain unresolved delivery evidence, not failure. Dedup ACK/echo across sessions via verified observation/alias only; use original outbound reservation identity + connection scope and preserve uncertain result until reconciliation. 
## 3. Routing and policies 
- Admin-only explicit primary+secondary designation; deterministic validated primary, no “latest ready” or random selection. Agent may choose eligible secondary within verified channel. Channel readiness (at least one eligible connected session) vs sender eligibility (role, current epoch, credentials, consent, Pilot, caps, manual pause, circuit, activation) separate. Default only primary, if unavailable require selection (no implicit new sender). An outbound intent binds channel, exact selected connection, membership epoch, recipient, payload fingerprint, stable idempotency key at reservation. Never silently change pending work/reservation on failover or reconnect. No blind resend if provider acceptance unknown. Explicit recovery only after proven pre-dispatch failure or independently reconciled non-delivery and policy/role check; preserve original attempt history.
- Provider caps remain; add channel-level aggregate protection/atomically shared usage before multi-session send activation so switching sessions cannot evade caps or consent. No new parallel guardrail or queue. Task/broadcast frozen connection, approvals and recipient do not change; multi-session inbound dedup must not change correlation. 
- Meta window based only on trusted same Meta channel/connection inbound, server recheck and approved templates. OpenWA same-number sessions share history but not credentials, native chat IDs or guardrail state; no Meta 24h check. Reply/read/reaction require independently verified native route on exact selected connection (or documented safe alias); if unavailable block rather than transplant JID/ID. CRM/channel read once, provider receipt per eligible explicit route; do not clear sibling channel.
## 4. UX/API
- GET /api/inbox/channels or compatible safe catalog returns channel id/display name/provider/identity state/readiness/known unread, primary and eligible session labels; no credentials/native IDs. GET threads scope=active|historical|unknown&channel_id (optional session diagnostic view limited to observed events; not a second thread/list count); history by thread id and same tenant/channel. “All connections” means unique active channels; archived sessions with a live same-channel replacement do not hide history. Historical channels (no active verified member) read-only; unknown lane explicit. Session filter for diagnostics only, not duplicate unread or independent CRM history. Legacy ?c and ?connection links resolve by verified historical membership with ambiguity selector, never silently choose sender. 
- Thread header stable number/channel, current primary and explicit valid sender selection in composer; changing session in same channel does not clear transcript or unread/draft; switching channel does. Session changes during send trigger server policy/epoch recheck. Provider readiness, primary status and policy denial visibly distinct. 
- Draft/read/status/account boundaries and p95 budgets in ADR-001 remain. Channel count != connection count. One user can have several independent channels for several numbers.
