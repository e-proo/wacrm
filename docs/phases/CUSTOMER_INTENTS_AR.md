# ذاكرة النوايا العامة ومطابقة الخدمات — تكامل الوكيل مع أي خدمة

> **الفرع:** `phase-5/operational-hardening`
> **الحالة:** مكتملة برمجياً، بانتظار تطبيق Migration 057 في Supabase ومراجعة المستخدم
> **الهدف:** يمكّن وكيل الذكاء الاصطناعي من خدمة أي طلب عميل — حتى الخدمات غير المجهزة في المنصة — دون اختراع حقول أو أسعار أو وعود.

## 1. المشكلة التي تحلها

سيناريو واقعي من عمل المكاتب:

1. العميل (أ) لديه تغطية بمبلغ في المكلاء.
2. بعد فترة، العميل (ب) يبحث عن تغطية في المكلاء.
3. الوكيل يتذكر الملاحظة الأولى، يرى التوافق، يخبر الرقم الإداري.
4. الإداري يوافق → الوكيل يؤكد للعميل. أو يرفض. أو يتولى بنفسه.

وقد تمدد السيناريو لأي خدمة مصرفية: حوالات داخلية وخارجية، شراء وبيع عملات، تغطيات بأنواعها، وغيرها — **بما في ذلك خدمات لم تُجهز بعد في المنصة**.

المشكلة الجوهرية: عندما يأتي طلب لا تنطبق عليه مخططات الخدمات المجهزة، ماذا يفعل الوكيل؟ الجواب الخاطئ هو "يخترع حقولاً أو يجبر الطلب على المخطط". الجواب الصحيح هو ما نفذناه أدناه.

## 2. القاعدة الحاكمة: ثلاثة مسارات فقط

```text
1. مطابقة تامة   (exact)   → خدمة مجهزة، كل الحقول المطلوبة موجودة، لا حقول غريبة.
2. مطابقة جزئية  (partial) → الخدمة تناسب، لكن حقل مطلوب واحد ناقص أو ذكر حقول غير معلنة
                              → الوكيل يسأل العميل عن النواقص.
3. لا مطابقة     (none)    → الوكيل يسجل "نية عامة" + يصعّد للإداري. ولا يخترع شيئاً.
```

لا يوجد مسار رابع. التحقق من المخططات يبقى صارماً (DENY BY DEFAULT) ولم نُخففه أبداً.

## 3. المكونات الجديدة

### 3.1 جدول `customer_intents` — الذاكرة العامة (Migration 057)

الصف الواحد = ملاحظة منظمة عن حاجة عميل:

| الحقل | الغرض |
|---|---|
| `contact_id` | العميل صاحب النية. |
| `conversation_id` | المحادثة المصدر. |
| `direction` | `offer` (يقدم) أو `request` (يطلب) — نفس أدوار نموذج التغطية. |
| `service_hint` | نص قصير لما فهمه الوكيل (حتى 300 حرف): "حوالة خارجية إلى كوالالمبور". |
| `summary` | ملخص بشري للإداري (حتى 2000 حرف). |
| `attributes` | JSONB حر بما فهمه الوكيل (مدينة، مبلغ، عملة...) — **لا يُدمج أبداً في مخطط مجهز**. |
| `status` | `new` → `clarifying` → `forwarded_to_admin` → `fulfilled` / `rejected`، أو `matched` عندما تُجهز الخدمة لاحقاً. |
| `matched_service_id` | يُملأ عندما تجهز خدمة مطابقة فتُربط النية بها. |
| `change_request_id` | يُملأ عند التصعيد الإداري. |
| `idempotency_key` | مفتاح فريد يمنع تكرار نفس الملاحظة عند إعادة تشغيل الوكيل. |

RLS: قراءة لأعضاء الحساب، كتابة admin+، لا حذف (تاريخ تدقيقي).

دوال service-role:

- `create_customer_intent(...)` — إنشاء ذري idempotent.
- `match_customer_intent(...)` — ربط نية بخدمة مجهزة لاحقاً (`status='matched'`).

كما وُسّعت قائمة `change_requests.target_type` لتشمل `service_intent`، فيمر التصعيد عبر **نفس محرك الاعتماد** (رمز تأكيد، انتهاء صلاحية، تدقيق) الذي تعتمد عليه بقية العمليات.

### 3.2 أدوات الوكيل الجديدة (3 أدوات)

| الأداة | الصلاحية | الوظيفة |
|---|---|---|
| `services.match_request` | read | تطابق طلب العميل على الخدمات المجهزة وتعيد `exact/partial/none` مع الحقول الناقصة والغريبة. |
| `intents.record` | **propose** | تسجل ملاحظة عامة عن العميل، واختيارياً تصعّد للإداري (تولّد `change_request` برمز اعتماد). |
| `intents.search` | read | تبحث في ذاكرة النوايا (بجهة اتصال، حالة، أو نص حر) — هنا "يتذكر" الوكيل ملاحظته القديمة. |

ملاحظة أمنية مهمة: `intents.record` صلاحيتها `propose` وليست `read` — يعني الوكيل لا يستطيع استخدامها إلا إذا مُنح صلاحية اقتراح صريحة في إصداره، وهو مسار خاضع لاعتماد المالك في المنشئ.

### 3.3 سلوك المطابقة بالتفصيل

`services.match_request` تقرأ الخدمات النشطة + تعريفات حقول مخططها المنشور، ثم تصنف كل مرشح:

- **exact**: كل الحقول المطلوبة موجودة، ولا حقول غريبة.
- **partial**: حقل مطلوب واحد ناقص (الوكيل يسأل)، **أو** ذكر العميل حقول غير معلنة (تظهر في `unknown_fields` ليأخذها الإداري بالحسبان عند تجهيز مخطط أغنى).
- **none**: حقلان مطلوبان ناقصان أو أكثر — أو لا خدمة مجهزة أصلاً تشبه الطلب.

النتيجة الإجمالية = أفضل تصنيف بين المرشحين، مرتبة `exact` ثم `partial` ثم `none`.

### 3.4 التصعيد الإداري

عند `none` (أو وقتما يرى الوكيل ذلك مناسباً): `intents.record` مع `escalate_to_admin=true` يفعل:

1. ينشئ النية (`customer_intents`).
2. ينشئ `change_request` نوع `service_intent/create` — يظهر في تبويب "طلبات التغيير" برمز اعتماد عادي.
3. يحدّث حالة النية إلى `forwarded_to_admin` ويربطها بالطلب.

قرار الإداري عند الاعتماد (`POST /api/change-requests/[id]/execute`):

- `fulfilled` — عالج الطلب يدوياً وأغلق النية.
- `rejected` — ارفض.
- `clarifying` — أعد للسؤال.
- `matched` — الجهزت الخدمة: يتطلب `matched_service_id` (يُتحقق أن الخدمة موجودة في الحساب) فتُربط النية بها وتصبح `matched`.

### 3.5 دورة حياة السيناريو الكاملة

```text
عميل: "أريد إرسال حوالة إلى كوالالمبور"
→ services.match_request → none (الحوالات الخارجية غير مجهزة)
→ intents.record (نيّة عامة + escalate_to_admin)
→ change_request CHG-N برمز اعتماد → تبويب طلبات التغيير
→ الإداري: يجهز خدمة "حوالات خارجية" من واجهة الكتالوج
→ execute برقم decision=matched + matched_service_id
→ النية تصبح matched ومربوطة بالخدمة
→ كل طلبات الحوالات القادمة = exact تلقائياً عبر الخدمة الجديدة
```

## 4. التكامل مع الموجود

- **نموذج التغطية**: `direction` بنفس دلالتي offer/request، لذا مطابقة "تغطية في المكلاء" تتم عبر أدوات التغطية الحالية + `intents.search` لاسترجاع الملاحظة القديمة عن العميل (أ).
- **محرك الاعتماد**: نفس `change_requests` — لا نظام اعتماد موازٍ.
- **سجل التدقيق**: كل إنشاء/تحديث نية يكتب في `service_activity_events`.
- **المنشئ**: Migration 057 يضيف الأدوات الثلاث إلى القوالب المقترحة لقوالب `customer_service` و`services_pricing` و`coverage` تلقائياً (بدون تكرار).
- **المراقبة**: أحداث النوايا تظهر في تبويب النشاط (`customer_intent.created/updated/matched`).

## 8. خطوات التشغيل في Supabase

1. طبّق `supabase/migrations/057_customer_intents.sql` في staging.
2. تحقق:

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = 'public' AND table_name = 'customer_intents';

SELECT system_template_key, suggested_tool_keys
FROM ai_agent_templates
WHERE system_template_key = 'customer_service';
-- يجب أن تشمل suggested_tool_keys أدوات intents وmatch_request
```

3. اختبار RLS بحسابين: نية في الحساب (أ) لا تظهر لحساب (ب).
4. جرّب الدورة: سجّل نية بـ escalate → اعتمدها من تبويب طلبات التغيير → نفّذها بـ decision.

## 9. حدود معروفة (مقصودة)

- `attributes` حر الشكل عمداً — هو ذاكرة، ليست مخططاً. التحويل إلى مخطط حقيقي يحدث فقط عبر تجهيز الخدمة من الكتالوج بواسطة الإداري.
- التصعيد الحالي ينتهي بربط النية بخدمة مجهزة أو إغلاقها يدوياً؛ إنشاء مخطط الخدمة الجديد نفسه يتم من واجهة الكتالوج الحالية (وليس تلقائياً من الاعتماد) — قرار مقصود لإبقاء منفذ التنفيذ حتمياً وضيقاً.
- الربط التلقائي مع نموذج اللغة الحقيقي (tool-calling loop) يبقى المتطلب التشغيلي الوحيد لتشغيل السيناريو بالكامل بدون تدخل يدوي.
