# المرحلة الرابعة — منشئ الوكلاء الآمن

> **الفرع:** `phase-3/tool-integrations-approvals`
> **الحالة:** مكتملة برمجياً، بانتظار تطبيق Migration 055 في Supabase ومراجعة المستخدم قبل الإغلاق والالتزام
> **مهم:** لم يتم إنشاء commit جديد احتراماً لتعليمات عدم الالتزام قبل تأكيد المستخدم.

بدأت المرحلة الرابعة فوق نواة الوكلاء وسجل الأدوات والاعتمادات من المرحلتين السابقتين. الهدف هو تمكين المستخدم المخول من إنشاء وكيل من قالب مسجل، مع إبقاء الأدوات والمسارات والاعتمادات داخل حدود النظام.

## 1. ما تم تجهيزه

### Migration 055

أضيفت الجداول التالية:

- `ai_agent_templates`: قوالب نظامية أو قوالب مملوكة للحساب.
- `ai_agent_test_cases`: حالات اختبار منظمة لكل وكيل.
- `ai_agent_evaluation_runs`: نتائج تشغيل الاختبارات بدون إرسال أو آثار إنتاجية.
- `ai_agent_budget_policies`: حدود التشغيل والرموز والتكلفة والإجراء عند بلوغ الحد.

القوالب النظامية المزروعة:

- `customer_service`
- `services_pricing`
- `coverage`
- `admin_services`
- `triage`

القوالب النظامية للقراءة فقط، أما القوالب المملوكة للحساب فتخضع لـ RLS وصلاحية admin+.

### API القوالب

أضيف:

```text
GET /api/ai-agent-templates
```

يعيد قوالب النظام وقوالب الحساب الحالي فقط.

### إنشاء وكيل من قالب

تم توسيع:

```text
POST /api/ai-agents
```

ليدعم مسارين:

1. المسار القديم: تعديل/نشر إصدار لوكيل موجود عبر `agentId`.
2. المسار الجديد: إنشاء وكيل جديد من قالب عبر `templateId` و`name` و`slug` الاختياري.

المسار الجديد:

- يتحقق من القالب وأنه نشط ومتاح للحساب.
- يختار اتصال مزود نشطاً تلقائياً عند عدم تحديده.
- ينشئ هوية وكيل بدون `system_key`.
- ينشئ الإصدار الأول كـ `draft`.
- ينسخ الإعدادات الافتراضية للقالب.
- ينسخ الأدوات المقترحة بعد تقاطعها مع سجل الأدوات الفعلي، ويسقط الأدوات غير المعروفة.
- لا ينشر الإصدار تلقائياً؛ المسودة تحتاج مراجعة ونشر منفصل.

### واجهة اختيار القالب

أضيف مكوّن:

```text
src/components/agents/agent-template-picker.tsx
```

يوفر:

- زر إنشاء وكيل جديد.
- عرض القوالب النظامية وقوالب الحساب.
- اختيار القالب.
- إدخال اسم الوكيل و`slug`.
- إنشاء المسودة.
- رسالة واضحة بأن الوكيل سيبقى مسودة حتى إكمال الإعداد والنشر.

تم ربطه مع `MultiAgentPanel`.

### تحقق الإصدار والنشر

أضيفت خدمة `builder-service.ts` لتطبيق قائمة تحقق موحدة قبل النشر:

- الوكيل والإصدار ينتميان للحساب.
- الوكيل ليس مؤرشَفاً.
- الإصدار `draft` فقط قابل للنشر.
- النموذج موجود.
- منح الأدوات معروفة وإصداراتها صحيحة وصلاحياتها مسموحة.
- عدد جولات الأدوات غير سالب، ولا يمكن تفعيل الجولات بدون منح.
- تعارضات المسارات الخطيرة تمنع النشر.
- غياب سياسة ميزانية يعطي تحذيراً ولا يمنع النشر، لأن سياسة الحساب الافتراضية قد تكون مطبقة.

المسارات:

```text
POST /api/ai-agents/[id]/revisions/[revisionId]/validate
POST /api/ai-agents/[id]/revisions/[revisionId]/publish
```

النشر يستدعي التحقق أولاً، لذلك لا يمكن تجاوز قائمة التحقق باستدعاء API النشر مباشرة.

### حالات الاختبار والمحاكاة

أضيفت:

```text
GET  /api/ai-agents/[id]/test-cases
POST /api/ai-agents/[id]/test-cases
POST /api/ai-agents/[id]/revisions/[revisionId]/evaluate
GET  /api/ai-agents/[id]/evaluations
```

المحاكاة الحالية آمنة وحتمية؛ لا تستدعي مزود AI، ولا ترسل واتساب، ولا تعدل بيانات الأعمال.

### الميزانيات والأدوات

أضيفت:

```text
GET /api/ai-agents/[id]/budget
PUT /api/ai-agents/[id]/budget
GET /api/ai-agents/[id]/tools
```

### تنفيذ طلبات التغيير المعتمدة

أضيف:

```text
POST /api/change-requests/[id]/execute
```

يدعم حالياً التنفيذ الحتمي لنشر قواعد التسعير ونشر إصدارات دفاتر أسعار الصرف فقط. أي هدف آخر يُرفض، ولا يوجد SQL أو كتابة عامة من النموذج.

### محلل تعارض المسارات

أضيف:

```text
src/lib/ai/runtime/route-conflicts.ts
```

ويصنف التعارضات إلى:

- **blocker**: يمنع النشر، مثل default مزدوج أو admin route بلا هوية موثوقة أو تعادل غير حاسم.
- **warning**: تحذير، مثل قاعدة واسعة ذات أولوية أعلى تحجب قاعدة أكثر تحديداً.
- **info**: معلومة، مثل توجيه إلى وكيل متوقف.

أضيف endpoint:

```text
POST /api/agent-routes/analyze-conflicts
```

كما تم ربط فحص التعارضات بخدمة نشر الإصدارات؛ وجود blocker يمنع النشر ويعيد `ROUTE_CONFLICT`.

## 2. إصلاح backfill

تم اكتشاف أن الحسابات التي أضافت اتصال المزود من واجهة الاتصالات الجديدة قد لا تملك صفاً في `ai_configs`. كان المسار القديم يعيد:

```text
no_legacy_config
```

وبالتالي يبقى الحساب باتصال مزود ولكن بدون وكلاء.

تمت إضافة مسار بديل في `backfill-legacy.ts`:

- إذا لم يوجد `ai_configs`، يبحث عن اتصال مزود `active` أو `verified`.
- ينشئ وكيل `customer_service` وإصداراً أولياً وينشره.
- ينشئ `admin_operations` كمسودة.
- ينشئ default route وadmin route.
- يبقى التنفيذ idempotent إذا كان وكيل خدمة العملاء منشوراً مسبقاً.

كما أضيف زر في حالة فراغ قائمة الوكلاء:

```text
POST /api/admin/backfill-legacy
```

ويظهر للمسؤول زر تشغيل التهيئة من واجهة الوكلاء.

## 3. الأدوات الحية من المرحلة الثالثة

الوكيل يستطيع الآن من خلال سجل الأدوات استخدام الأدوات المقروءة التالية بعد منحها للإصدار:

- `services.search`
- `services.get`
- `pricing.calculate_quote`
- `exchange_rates.get_current`
- `coverage.check_availability`

كل أداة:

- مسجلة مسبقاً.
- لا تقبل SQL أو URL أو اسم جدول حر.
- تقرأ من الحساب الحالي فقط.
- تعيد `safe_to_show` لمنع تسريب أخطاء داخلية.
